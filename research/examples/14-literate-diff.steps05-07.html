Making the view skill tell the truth about ranges

PR #5, steps 5–7 · fa718bf, ba53054, ef00662 · skills/view/SKILL.md · a "literate diff" in Geoffrey Litt's sense: the changes as prose, in the order that explains them. Hand-written from the commits.

By step 4 the view skill could turn almost anything into a range. These three steps fix the places where it would hand the viewer the wrong range, or a range with nothing in it. They read best in the order the PR case, the empty check, the root commit: each one is about a range that comes up empty or can't be shown.

A merged PR should still have its commits step 5 · fa718bf

The skill took a PR's base as its merge-base with today's base branch. That works for an open PR. Once a PR is merged with a merge commit, though, its head is already inside the base branch, so the merge-base is the head, and the range is empty. PR #4 resolved to zero commits.

GitHub already knows the base as the PR saw it: baseRefOid. Merge-basing against that gives PR #4 its 7 commits, and for an open PR it is the same answer as before.

-  gh pr view <n> --json headRefName,baseRefName,title-  git fetch origin "pull/<n>/head:refs/pr-timeline/<n>" "<baseRefName>"+  gh pr view <n> --json baseRefOid,title+  git fetch origin "+pull/<n>/head:refs/pr-timeline/<n>" <baseRefOid>

Two smaller things ride along. Fetching the SHA directly still works after the base branch is deleted. And the leading + on the head fetch lets a re-fetch follow a force-push; without it git refuses a non-fast-forward update, which made the old line "re-fetching is safe" untrue.

-  HEAD = `refs/pr-timeline/<n>`, BASE = `git merge-base origin/<baseRefName> refs/pr-timeline/<n>`.+  HEAD = `refs/pr-timeline/<n>`, BASE = `git merge-base <baseRefOid> refs/pr-timeline/<n>`.

Count the range the way the viewer does step 7 · ef00662

The skill already said "If HEAD has no commits over BASE, there is nothing to step through — report that instead of starting a server.", but gave no command. The obvious one, a plain rev-list --count, counts merges. Since step 2 the viewer skips merges, so a range of only merges would pass the check and then open on a blank viewer.

-If HEAD has no commits over BASE, there is nothing to step through — report that-instead of starting a server.+Then count what the viewer will step through. It skips merges, so count the same+way:++```+git -C <REPO> rev-list --count --no-merges <BASE>..<HEAD>+```++If that is 0, there is nothing to step through — report that instead of+starting a server. A branch already merged into the default branch lands here.

The commit names two real branches that resolve to 0 in this repo, viewer-disconnect and split-diff-toggle, both already merged.

A root commit can't be shown step 6 · ba53054

For a single SHA the base is its parent. For a root commit, which has no parent, the skill suggested the empty tree. That fails twice: the skill's own verify step rejects it (a tree is not a commit), and the server diffs every commit against its parent, so even launched by hand the root commit arrives with no files. Fixing that means changing the server, which is outside this branch, so the skill now just says so.

-- **A single SHA** — HEAD = the SHA, BASE = `<sha>^`. For a root commit, BASE =-  `git hash-object -t tree /dev/null` (the empty tree).+- **A single SHA** — HEAD = the SHA, BASE = `<sha>^`. A root commit has no+  parent and can't be shown (see below).

and, next to the note about merges:

+- **A root commit can't be shown.** Each step diffs a commit against its+  parent, and a root commit has none.
